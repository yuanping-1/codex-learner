## 2. 不直接采纳的结论和方案

| 评审表述 | 判断依据 | 处理 |
| --- | --- | --- |
| Windows 磁盘预写校验导致 14.80 倍延迟，可能由 NTFS/Defender 解释 | 20.5 秒与 1.385 秒来自不同环境的单次记录；没有控制磁盘、缓存、运行条件和完整工作负载 | 仅保留两项观察值；比值不作为平台因果证据，不据此建议关闭扫描或设置排除 |
| 每次 1,000–3,000 次打开、平均单文件毫秒数、累计百万次 I/O、去重减少约三分之一 | 数量和文件大小是假设，当前去重已存在；云端历史基准实际批量构造数据后测一次操作 | 不写成实测或收益承诺；改为记录实际唯一引用、打开及哈希次数 |
| 用大小/mtime、签名缓存及周期抽样替代跨事务全文校验 | 等长改写并恢复 mtime 可以绕过元数据判断；缓存签名不证明正文未变；抽样会遗漏损坏 | **不采用为当前优化路线**。只有能证明等价完整性保证的失效机制才值得另行评估 |
| RGB/FP32 像素理论大小说明 OCR 整体内存达标 | 这只覆盖部分缓冲区，不包括模型、临时张量、解释器及进程组所有占用 | 可以解释渲染约束，不能替代 RSS/提交内存及目标机器实测 |
| 第一张图以 `74/75=98.7%` 展示包完整性 | 75 个 ZIP 成员中，74 个受清单覆盖，第 75 个是清单自身；不是 1 项没通过 | 不沿用该图；正确口径是“74 个受清单覆盖成员全部匹配，整包另核验 SHA-256” |

| 架构图把不可变正文和清单落盘只画在 `assess` 之后 | `submit_answer` 必须先持久保存原答和 pending 状态，之后才可恢复评价 | 保留工程报告原有时序图，明确两次独立事务；不称为分布式两阶段提交协议 |

理论模型可以用于形成测量假设，但不能把假设参数除以总耗时后得到的数值称为实际单文件成本。附件中的 `unknown_url` 也不能为这些推演提供可核查依据。
