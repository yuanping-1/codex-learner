## 2. 性能对比

从候选源码目录使用其 `scripts/benchmark_history.py` 驱动基线和候选。所有课程由基准生成，不给基准传入正式库。

```text
<同一 Python> <候选源码>/scripts/benchmark_history.py --records 1000 --repeat 30 --warmup 3 --operations submit,retry --baseline-root <基线源码目录> --output <本轮证据目录>/performance-comparison.json
```

随后另跑诊断，不能将其时延与无探针测量混合：

```text
<同一 Python> <候选源码>/scripts/benchmark_history.py --records 1000 --repeat 1 --warmup 0 --operations submit,retry --profile --baseline-root <基线源码目录> --output <本轮证据目录>/performance-profile.json
```

使用本机 shell 正确引用含空格的路径。每条命令保存原始 stdout/stderr 和退出码；不能只保留最终汇总。

应核对：

- 同一合成快照及每样本相同初始状态，构建与复制不计入日常操作时延和内存。
- 新提交与原请求重试分组；重试命中原回执，不增加作答、评价、操作和修订号。
- 全部原始样本、预热标记、样本数、中位数、P95 算法、最大内存与失败数保留。
- 文件访问统计是应用层读/打开/哈希，不是物理磁盘 I/O；新进程不等于操作系统冷缓存。
- 核心 256 MiB 是初始内存目标；中位数 2 秒/P95 5 秒是待目标机确认的体验目标。未达到时报告实际值，不提高目标或删去慢样本。

若依赖或机器条件阻止测量，记录 BLOCKED 及实际错误。若出现功能失败或数据不一致，记录 FAIL 并保留样本目录；不能只把失败样本从百分位中排除后宣布通过。

## 3. 存储正确性及原五项复验

从候选源码运行新增正文完整性测试及受影响的存储、恢复、归档、安装回归。重点确认：

- JSON 原始字节先完整核验，再严格解析；重复键、NaN、无效 UTF-8、长度或哈希不符被拒绝。
- 同一 JSON 被多处引用只在一次完整性遍历中读取一次，传递引用仍全部检查。
- 成功校验后再等长改写正文并恢复 mtime，下一次写入仍失败；`course.json` 和 `course.previous.json` 不被覆盖。
- 原答 CRLF/空白/Unicode 保持，同 ID 重试去重，提交回读失败后可沿原 ID 恢复。
